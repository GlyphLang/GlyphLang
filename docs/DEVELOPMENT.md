## Common Workflows

### Build

```bash
# Build the CLI binary
make build

# Or directly with Go
go build -o glyph ./cmd/glyph/
```

### Test

```bash
# Run all tests
make test

# Or directly
go test ./...

# Run a specific package
go test ./pkg/parser/...

# Run a single test by name
go test -run TestLexer_Symbols ./pkg/parser/

# Run with coverage report
go test -cover ./...
go test -coverprofile=coverage.out ./... && go tool cover -html=coverage.out
```

### Lint

```bash
make lint

# Or directly
go vet ./...
golangci-lint run   # requires golangci-lint installed
```

### Development server with hot reload

```bash
glyph dev examples/todo-api/todo.glyph
```

### Inspect generated bytecode

```bash
glyph compile examples/hello-world/hello.glyph -o hello.glyphc
glyph decompile hello.glyphc
```

### Validate a .glyph file (structured JSON error output)

```bash
glyph validate myfile.glyph
```

### Generate AI-optimized context for an LLM

```bash
glyph context examples/todo-api/todo.glyph --format compact
```

## How to Add a New Opcode

Opcodes are 1-byte instructions executed by the stack-based VM in `pkg/vm/vm.go`. The current opcode table uses specific hex ranges by category:

| Range | Category |
|---|---|
| `0x01-0x02` | Stack |
| `0x10-0x14` | Arithmetic |
| `0x20-0x29` | Comparison and logic |
| `0x40-0x41` | Variables |
| `0x50-0x56` | Control flow and iteration |
| `0x61-0x62` | Function calls and return |
| `0x70-0x71` | Object operations |
| `0x80` | Array operations |
| `0x90` | HTTP |
| `0xA0-0xA9` | WebSocket |
| `0xB0-0xB1` | Async/await |
| `0xFF` | Halt |

New opcodes should be added at `0xB2` and above (up to `0xFE`), or into an unused gap in an existing category if the opcode belongs semantically there.

### Step 1: Define the constant

In `pkg/vm/vm.go`, add the opcode constant in the appropriate category:

```go
const (
    // ... existing opcodes ...

    OpMyNewOp Opcode = 0xB2 // Brief description of what it does
)
```

### Step 2: Add execution logic

In `pkg/vm/vm.go`, inside the `Execute()` method's main switch, add a case:

```go
case OpMyNewOp:
    operand := vm.popStack()
    result := doSomething(operand)
    vm.pushStack(result)
```

Study adjacent cases for the correct stack discipline. Most opcodes pop their inputs, compute, and push one result.

### Step 3: Emit the opcode from the compiler

In `pkg/compiler/compiler.go`, add or update the compile method that should emit the new opcode:

```go
func (c *Compiler) compileMyFeature(expr *ast.MyExpr) error {
    if err := c.compileExpression(expr.Operand); err != nil {
        return err
    }
    c.emit(OpMyNewOp)
    return nil
}
```

Wire the new method into `compileExpression()` or `compileStatement()` at the appropriate AST node case.

If the opcode takes an inline operand (like a jump offset or constant pool index), use `c.emitWithOperand(OpMyNewOp, operand)` instead.

### Step 4: Update the decompiler

In `pkg/decompiler/decompiler.go`, add the opcode name to the name mapping so `glyph decompile` shows a human-readable label:

```go
case vm.OpMyNewOp:
    return "MY_NEW_OP"
```

### Step 5: Write tests

- `pkg/vm/vm_test.go` — construct raw bytecode with the opcode, execute it in a VM, assert the result
- `pkg/compiler/compiler_test.go` — compile a .glyph snippet that exercises the new opcode, assert the bytecode contains it

### Step 6: Document the opcode

Add an entry to `docs/BINARY_FORMAT.md` in the opcode table with its hex value, name, stack effect, and operand format.

## How to Add a New Language Feature

Adding a new language construct (expression, statement, or declaration) touches multiple layers. Work through them in order.

### Step 1: Add tokens (if new syntax is needed)

In `pkg/parser/token.go`, add a constant for any new token the lexer must recognize:

```go
const (
    // ... existing tokens ...
    MY_KEYWORD TokenType = iota
)
```

In `pkg/parser/lexer.go`, add recognition logic. If it is a keyword, add it to the keywords map. If it is a new symbol, handle it in the main tokenization switch.

### Step 2: Add the AST node

In `pkg/ast/ast.go`, define the node struct and implement the `Node` interface:

```go
type MyExpr struct {
    Token token.Token
    Value Expr
    // ... fields
}

func (me *MyExpr) expressionNode() {}
func (me *MyExpr) TokenLiteral() string { return me.Token.Literal }
```

### Step 3: Parse the new construct

In `pkg/parser/parser.go`, add a parsing function:

```go
func (p *Parser) parseMyExpr() (Expr, error) {
    tok := p.currentToken
    p.advance()
    // parse sub-expressions
    value, err := p.parseExpression(LOWEST)
    if err != nil {
        return nil, err
    }
    return &ast.MyExpr{Token: tok, Value: value}, nil
}
```

Wire it into `parseExpression()` or `parseStatement()` at the right precedence level or token check.

### Step 4: Evaluate in the interpreter

In `pkg/interpreter/evaluator.go`, add an eval case:

```go
case *ast.MyExpr:
    return i.evalMyExpr(node)
```

Implement `evalMyExpr`:

```go
func (i *Interpreter) evalMyExpr(expr *ast.MyExpr) (interface{}, error) {
    val, err := i.eval(expr.Value)
    if err != nil {
        return nil, err
    }
    // ... compute result
    return result, nil
}
```

### Step 5: Compile to bytecode

In `pkg/compiler/compiler.go`, add a compile case:

```go
case *ast.MyExpr:
    return c.compileMyExpr(node)
```

Implement `compileMyExpr` following the pattern in Step 3 of [How to Add a New Opcode](#how-to-add-a-new-opcode).

### Step 6: Add to the IR (if codegen targets need it)

If the feature needs to survive into Python or TypeScript code generation, add a corresponding IR node in `pkg/ir/ir.go` and handle it in `pkg/ir/analyzer.go`. Then add output in the relevant generator (`pkg/codegen/python.go`, `pkg/codegen/typescript_server.go`).

### Step 7: Write tests

Add table-driven tests to all affected layers:

- `pkg/parser/parser_test.go` — input source → expected AST
- `pkg/interpreter/interpreter_test.go` — input source → expected runtime value
- `pkg/compiler/compiler_test.go` — input source → expected bytecode or output behavior

### Step 8: Document and add an example

- Update `docs/LANGUAGE_SPECIFICATION.md` with the new syntax and semantics
- Add a minimal working example to `examples/` if the feature is user-facing

### Feature checklist

- [ ] Token(s) added to `token.go` and `lexer.go`
- [ ] AST node defined in `ast.go`
- [ ] Parser rule added to `parser.go`
- [ ] Interpreter eval case added to `evaluator.go`
- [ ] Compiler emit case added to `compiler.go`
- [ ] IR node added if codegen targets need it
- [ ] Tests: parser, interpreter, compiler
- [ ] `LANGUAGE_SPECIFICATION.md` updated
- [ ] Example added if user-facing

## Debugging Tips

### Validate first

`glyph validate` produces structured JSON errors that pinpoint exactly where parsing or type checking failed:

```bash
glyph validate myfile.glyph
```

This is especially useful when debugging parser changes — the JSON output is machine-readable and easy to diff.

### Inspect bytecode

After a compile, disassemble the output to see what opcodes were emitted:

```bash
glyph compile myfile.glyph -o out.glyphc
glyph decompile out.glyphc
```

If an opcode you expected to see is missing, or appears in the wrong order, the issue is in the compiler's emit logic.

### Print in tests

In test code, `t.Logf` output is suppressed unless the test fails or `-v` is passed. Use it liberally:

```go
t.Logf("compiled bytecode: %v", bytecode)
t.Logf("AST: %+v", node)
```

Run with `go test -v -run TestMyTest ./pkg/compiler/` to see all log output.

### Trace the compiler symbol table

The compiler maintains a symbol table (`c.symbols`) for variable tracking. If a variable lookup fails at runtime but you expect it to be defined, add a temporary `fmt.Printf` around the emit site to verify the symbol is being registered correctly before the lookup.

### Check the optimizer separately

If behavior changes depending on optimization level, the optimizer in `pkg/compiler/optimizer.go` may be rewriting the bytecode. Run tests with optimization level 0 to isolate the issue:

```go
compiler := compiler.NewCompiler(compiler.OptNone)
```

## Deciding Where a Change Lives

Use this table when unsure whether to modify the interpreter, compiler, or both:

| Scenario | Where to change |
|---|---|
| New syntax that runs in `glyph run` (development mode) | Interpreter only (for now), compiler later |
| New syntax that should compile to a binary | Both interpreter and compiler |
| Performance improvement to an existing feature | Compiler + optimizer, possibly VM |
| Error message improvement | Interpreter (`evaluator.go` or `executor.go`) and/or parser (`parser.go`) |
| New built-in function | `pkg/interpreter/builtins_http.go` or a new `builtins_*.go` file |
| New HTTP-specific behavior | `pkg/server/handler.go` and interpreter executor |
| New codegen output | `pkg/ir/analyzer.go` + relevant `pkg/codegen/*.go` file |
| New CLI command | `cmd/glyph/commands.go` + `cmd/glyph/handlers.go` |
